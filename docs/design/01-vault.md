# Vault design

## Purpose

The vault is Maia's human-readable long-term mind: one Obsidian folder containing agents,
navigation indexes, personalities, and entity pages. It is not the event store. Conversation
transcripts, reasoning traces, prompt-cache slots, presentation logs, vectors, and dream batch
state live in the shared SQLite brain beside the vault.

**Supersession (2026-11-05):** accepted [`14-super-agent-router.md`](14-super-agent-router.md)
keeps these vault folders as human-edited personalities and entity notes. They are not the
sidebar's user-facing chat list. A task retrieves shared entities plus the private entities of
its participants.

The vault has two consumers:

- People edit human prose in Obsidian.
- Maia maps note metadata for navigation, reads note bodies only when explicitly requested, and
  projects accepted facts into generated regions.

The required layout is:

```text
vault/
  agents.md
  index.md
  agents/<agent>/index.md
  agents/<agent>/personality.md
  agents/<agent>/entities/index.md
  agents/<agent>/entities/<entity>.md
  world/entities/index.md
  world/entities/<entity>.md
```

`agents.md` explains how Maia works. `personality.md` is human-authored and is never a dream
target. Shared entities belong under `world/entities/`. Facts true only for one agent belong
under that agent's `entities/` folder. A thread may retrieve shared entities plus the private
entities of its participants, and no other agents' private entities.

## Note and frontmatter contract

Every Markdown file starts at byte zero with YAML frontmatter containing all four required keys:

```markdown
---
id: entity_maia
description: The local agentic operating system.
see:
  - "[[agents/scout/index]]"
  - "[[world/entities/obsidian]]"
kind: entity
---
```

The field contract is:

- `id`: a non-empty stable identifier unique across the vault. A rename may change the path but
  must not change this value. IDs are opaque strings; consumers must not infer a kind from an ID
  prefix.
- `description`: a non-empty, single-line plain-text summary used by generated indexes and
  `map`. It must not contain a fact body or folded/multiline YAML.
- `see`: a YAML sequence of zero or more vault-relative Obsidian wikilinks. Links use `/`, omit
  the `.md` suffix, and must not escape the vault.
- `kind`: the note category. The initial closed set is `root`, `agents`, `agent`, `personality`,
  `entities`, and `entity`. Adding a kind is a design change rather than an unknown-kind fallback.

UTF-8 without a BOM is canonical. Line endings in generated bytes are LF. Readers accept CRLF
outside a protected human region, but a renderer must preserve the protected bytes exactly.
Duplicate YAML keys, aliases, custom tags, invalid UTF-8, missing required fields, unknown fields,
unknown kinds, duplicate IDs, absolute links, and `..` path components are validation errors.
Frontmatter is metadata, not a substitute for a note body.

Example personality note:

```markdown
---
id: personality_scout
description: Scout's human-authored operating character.
see:
  - "[[agents/scout/index]]"
kind: personality
---
You investigate before proposing a change.
```

The personality body is entirely human-authored. A dream must neither create, rewrite, normalize,
nor delete `personality.md`.

**Approved instruction hashes.** `personality.md` and `agents.md` are installed into a new thread
log only at an owner-approved content hash (`10-security.md`, `Confirm`). A changed file raises a
`Confirm` request. Until approved, new threads use the last approved bytes; existing threads keep
the bytes already frozen in their durable prefix. An agent with no approved personality cannot
start a thread.

## Human and generated regions

Entity pages use exactly one generated region followed by exactly one human region:

```markdown
---
id: entity_obsidian
description: A local Markdown knowledge-base application.
see:
  - "[[world/entities/maia]]"
kind: entity
---
<!-- maia:generated:start -->
- `fact_01JABC`: Obsidian opens Maia's vault for human editing.
<!-- maia:generated:end -->
<!-- maia:human:start -->
## Notes

Keep local plugins minimal.
<!-- maia:human:end -->
```

The boundaries are literal ASCII byte sequences. The **human region** is every byte after the LF
ending `<!-- maia:human:start -->` and before `<!-- maia:human:end -->`; those bytes include all
whitespace and line endings. The **generated region** is the bytes between the equivalent
generated markers. Markers are structural and are not part of either region.

For an existing entity page, rendering may replace only the generated-region bytes. It must retain
the frontmatter and copy the human-region bytes without decoding, trimming, re-indenting, or
newline conversion. The frontmatter `id` must match the brain entity ID or rendering fails. Each
current fact appears once in the generated region as a Markdown list item containing its stable
fact ID and one-sentence text. Fact sentences and entity descriptions pass through
`neutralize_inline_markdown` (`10-security.md`) before they enter generated bytes: the output
contains none of the unescaped constructs that table forbids (`[[`, `![[`, `![`, `](`, HTML
openers, Templater/Dataview markers, `%%`, `<!-- maia:`, blocked schemes, UNC prefixes, or
bidirectional controls). The escape table is versioned with the renderer. Facts are sorted by
stable fact ID so the same state renders byte-identically.

A newly promoted entity uses the canonical shape above with an empty human region. A page with
missing, duplicated, nested, reversed, or malformed markers is not repaired automatically: the
write fails and the existing file remains untouched. Generated indexes do not have human regions;
their complete bodies are generated. Other human notes have no generated markers and are never
passed to the entity renderer.

## Generated index contract

Every folder has an `index.md`. Its frontmatter describes the folder; its body is a generated,
lexicographically ordered list of immediate child folders and notes, excluding that `index.md`.
Each entry contains only the child's wikilink and frontmatter `description`:

```markdown
---
id: entities_world
description: Shared entities.
see: []
kind: entities
---
- [[world/entities/maia]] — The local agentic operating system.
- [[world/entities/obsidian]] — A local Markdown knowledge-base application.
```

Ordering uses the normalized vault-relative link as a bytewise UTF-8 key. Index generation reads
child frontmatter only; it must not read or summarize child bodies. Rendering the same validated
children twice produces identical bytes. A write uses a temporary sibling, flushes it, and
atomically replaces the target where the filesystem supports replacement. A failure before
replacement leaves the prior index intact.

## `map` and `read` contracts

Paths are vault-relative, use `/`, and are resolved only after rejecting absolute paths, drive
prefixes, NUL, empty components, `.`, `..`, and symlink traversal outside the canonical vault
root. Callers may omit `.md` for files. Ambiguous folder/file resolution is an error.

The conceptual API is:

```text
map(path: Option<VaultPath>) -> Result<MapResult, VaultError>
read(path: NotePath) -> Result<NoteBody, VaultError>

MapResult =
  Index { path, frontmatter, entries }
  | NoteHeader { path, frontmatter }
```

- `map(None)` returns the parsed root `index.md`.
- `map(Some(folder))` returns that folder's parsed `index.md`.
- `map(Some(file))` returns only that file's parsed frontmatter.
- `map` never returns a non-index note body. Folder index entries contain only links and
  descriptions obtained from child frontmatter.
- `read(file)` returns every byte after the closing frontmatter delimiter. It does not return
  frontmatter. For entity pages this includes both region markers and both region bodies.
- `read` rejects folders. Reading an index explicitly is allowed and returns that index body;
  this does not permit reading any child's body.

Neither operation follows a frontmatter `see` link implicitly. Neither operation writes,
regenerates, calls a model, consults the brain, or changes access according to content. Thread
retrieval policy decides which already-read paths may enter a prompt.

Errors distinguish `InvalidPath`, `OutsideVault`, `NotFound`, `AmbiguousPath`,
`InvalidFrontmatter`, `DuplicateId`, `InvalidRegionMarkers`, and `Io`. Error values include the
vault-relative path but never substitute partial content as success.

## Dream projection contract

The authoritative dream batch schema and transaction sequence are defined in
[05-dream.md](05-dream.md). The vault participates only after the batch's facts, entity IDs,
merges, and closures have committed in one SQLite transaction:

1. Read the committed current facts and entity identities.
2. Render affected entity pages in memory, validating markers and preserving human bytes.
3. Replace all successfully staged entity pages.
4. Regenerate affected folder indexes from child frontmatter, bottom-up.
5. Record projection completion in the brain.

The filesystem is not part of the SQLite transaction. Projection is therefore an idempotent,
recoverable second phase, not a claim of cross-store atomicity. A retry derives bytes from the
committed brain state; it never repeats the model call and never mutates human bytes.

## Invariants

1. A dream never writes `personality.md`.
2. A dream leaves every existing entity human region byte-identical, including whitespace and
   line endings.
3. `map` returns navigation metadata and links, never a non-index note body.
4. `read` has no implicit traversal, retrieval, generation, or write side effect.
5. Generated output is deterministic for the same validated inputs.
6. Stable note and fact IDs survive path renames and regenerated prose.
7. Shared and agent-private entity namespaces remain distinct; a thread sees only shared entities
   and private entities belonging to its participants.

## Failure handling

- Invalid frontmatter or duplicate IDs blocks the affected map/index/projection operation and
  reports the path; Maia does not guess or silently drop the note.
- A malformed entity boundary blocks that entity's projection before replacement. Its original
  bytes remain in place and the dream projection remains pending for retry.
- Missing parent indexes are generated only after all child headers validate.
- A partial filesystem projection is safe: already replaced files equal the committed state, and
  pending files are retried from that same state. Index completion is recorded only after all
  affected pages and indexes succeed.
- Concurrent human edits are detected by comparing each source file's pre-render content hash
  immediately before replacement. A changed file is not overwritten; the projection is retried
  against the new bytes.
- I/O and permission errors preserve the previous target, retain a pending projection, and surface
  a durable error. They never roll back an already committed brain batch.
- A watcher event caused by Maia's own deterministic write may trigger revalidation but must not
  create another dream or rewrite loop.

## Testing contract

Tests must be written from fixtures with independent expected bytes:

- Parse valid frontmatter and reject every invalid case named above.
- Assert `map(None)`, folder map, and file map return the specified variants and that a sentinel
  child-body secret never appears in any map result.
- Assert `read` returns the exact post-frontmatter bytes and rejects folders and traversal.
- Render an entity containing mixed line endings, blank lines, trailing spaces, non-ASCII text,
  and marker-like text outside marker lines; assert the protected human byte slice is identical.
- Assert malformed or duplicate boundaries produce an error and leave the fixture unchanged.
- Assert deterministic fact and index ordering and byte-identical repeated renders.
- Assert a dream target cannot resolve to `personality.md`.
- Simulate a concurrent edit between staging and replacement; assert no human byte is lost.
- Simulate failure after one page replacement and before index completion; retry and assert the
  final files equal a clean uninterrupted projection.
- Assert participant-scoped retrieval cannot include a nonparticipant's private entity path.
- Assert `neutralize_inline_markdown` strips or escapes every forbidden construct from
  `10-security.md` and that a rendered entity page still parses to exactly one generated and one
  human region.
- Assert a changed `personality.md` without a new approved hash cannot open a thread, while the
  last approved hash still can.

Filesystem integration tests use a temporary real directory for replacement, symlink, and
concurrent-change behavior. Pure parser and renderer tests use byte fixtures and perform no I/O.

## Explicitly out of scope

- Storing transcripts, reasoning, prompt caches, vectors, presentation logs, or raw episodes in
  Markdown.
- A second Markdown editor inside Maia; Obsidian remains the editor.
- Model-generated navigation on each `map` or `read`.
- Fine-tuning, semantic ranking, embeddings, activation, or PageRank.
- Promotion and dream extraction policy and model prompting, except for the projection boundary above.
- Sync, merge-conflict resolution, backup, encryption, Obsidian plugin management, and remote
  filesystem access.
- Following links automatically or granting one agent access to another agent's private entities.
